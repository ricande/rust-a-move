# Technical design

Build on the audited RustyHusky source in `08_TEMPLATE_AUDIT.md`. The following module names and interfaces are proposed new code, not existing template APIs.

## 1. Boundaries

Keep the template as one binary crate initially. Select `grin::GrinGame` through `ActiveGame` in `main.rs`. Put game code below `src/grin/`:

| Module | Responsibility |
| --- | --- |
| `mod.rs` | Implements `Game`, game-local setup, state orchestration and sound queue. |
| `board.rs` | Cells, entity ids, six-neighbour graph, connectivity. |
| `geometry.rs` | Layout, world/cell mapping, collision and swept corridors. |
| `shot.rs` | Shared prediction/launch path, contact and attachment selection. |
| `resolve.rs` | Match, blast closure, unsupported removal and scoring events. |
| `escape.rs` | Route choice, timer, deterministic departure. |
| `emotion.rs` | Pure expression targets and timed animation state. |
| `render.rs` | Procedural creature drawing through View. |
| `rules.rs` | Validated round rules and tunable defaults. |
| `content.rs` | Embedded levels, validation, seeded generation. |
| `rng.rs` | Owned RNG with explicit algorithm/version. |
| `text.rs` | Game EN/SV translation entries. |
| `persistence.rs` | Game config file IO, isolated from simulation. |
| `lab.rs` | Selectable animation test scenarios. |

Start with fewer files if easier; split along these boundaries as real code grows. No ECS, scripting language, plugin framework, physics engine or asynchronous simulation is needed. Macroquad value math types are allowed in headless code; no window, global input, audio or graphics calls there.

## 2. Board model and coordinates

Use `Cell { row: u16, col: u16 }` with deterministic row-major ordering and immutable `CreatureId(u64)` assigned monotonically per round. Store cells in a bounded row-major Vec; maintain an id→cell index if it earns its complexity. Avoid iteration-dependent HashMap behaviour in rules. `Creature` contains id, kind (`Ordinary(Family)` or `Angry`), optional Runner state and animation seed. Runner is allowed only on Ordinary.

For long-row count N and common collider radius r:

- Even rows have N cells; odd rows have N−1.
- Horizontal centre spacing is 2r; vertical pitch h = sqrt(3)r.
- Centre x = left + r + 2r·col + (row mod 2)r.
- Centre y = ceiling_y + r + row·h.
- Even-row diagonals in each adjacent row have columns col−1 and col.
- Odd-row diagonals in each adjacent row have columns col and col+1.
- Same-row neighbours are col−1 and col+1; reject invalid cells.

Top row's collider top touches the ceiling. Ceiling descent adds h to `ceiling_y`; rows/parity never renumber. Compute centres from Cell+layout each time; do not accumulate float movements per creature. Use f64 for trajectory calculations, convert to f32 only for drawing.

Define board width and safe regions in logical 540×960 coordinates. Board left/right are projectile bounce planes; projectile centre reflects at left+r and right−r. Launcher centre lies below the danger line by more than 2r at every supported width. A separate setup preview validates fit for the largest radius. Store rule distances in units of diameter or radius and map through layout.

Different silhouettes fit within the common radius. A square's corners are inscribed in the collider; a diamond is a rotated square. Eyes and eyebrows may extend slightly but never imply a larger collision surface. Have an optional debug collider overlay in the lab only.

## 3. Trajectory calculation

Use continuous collision, not frame-by-frame overlap. For a projectile centre p and normalized direction d, test ray intersection against occupied centres with expanded radius 2r, ceiling plane at ceiling_y+r, and side planes at left+r/right−r. Only nonnegative forward distances above epsilon are candidates; discard self-contact generated by a reflection. Solve circle roots robustly; a tangent counts as contact. At simultaneous contacts within tolerance prefer creature over wall/ceiling, then stable CreatureId; wall/ceiling corner ties use a documented deterministic order.

Continue reflecting direction at side planes until first creature or ceiling contact. Valid angle range guarantees positive upward progress. Derive a generous safety cap from board height, minimum allowed upward component and narrowest corridor; validate all layouts against it. A 128-reflection diagnostic bound is a starting guard, not a reason to truncate a valid shot silently.

Return `ShotPlan { segments, first_hit, attachment, travel_distance, board_revision }`. Reuse this exact plan for aim reaction and shot execution. `first_hit` identifies the physical creature hit, independently of whether attachment is possible. A direct angry impact has no attachment. Invalid attachment can still make an ordinary target afraid before the losing shot.

On Fire, recompute against the latest revision, then freeze occupancy/ceiling/escape mutations until the impact transaction completes. Advance scalar distance along segments at speed·FIXED_DT; if several segments fit within one update consume them all. At final distance resolve once. This guarantees that the fearful target is actually hit despite display frame rate or cosmetic shaking.

## 4. Attachment selection

For creature contact, candidates are valid empty six-neighbours of the struck cell. Reject candidates whose centre is outside the side bounds, above the ceiling, overlapping occupied circles (apart from exact packing contact), or unreachable from the impact point without crossing another expanded occupied circle. The short snap segment may touch the target but cannot pass through its interior or another creature; define allowable tangency in tests. Choose smallest squared distance from projectile contact centre to candidate centre; ties use row then column. If none is valid: `BoardBlocked`.

For ceiling contact consider empty top-row cells adjacent in x to the contact location, at most one diameter from it; validate the same short swept snap. Choose nearest, then smallest column. Do not use round-to-grid across the entire board, overwrite occupancy or attach on the far side of an obstacle. Test three-way junctions and narrow gaps before tuning visuals.

## 5. Rule transaction and events

Pure logical functions return typed events and a new state, or mutate through one controlled transaction. Example events: `Attached`, `Matched`, `Exploded`, `Detached`, `Escaped`, `CeilingLowered`, `RoundEnded`. Include ids, cells, cause and deterministic sequence number. Snapshot pre-removal centres for presentation. Simulation emits events once; rendering never emits events or SFX.

Resolution order is fixed:

1. Validate current shot-plan revision (a mismatch is a programming fault).
2. Direct angry contact → compute complete blast closure; otherwise attach → find family component → remove iff count >= 3.
3. Remove unsupported components from the resulting occupancy.
4. Update score once per id and generate bounded presentation/audio events.
5. Increment the shot counter exactly once for a fired shot.
6. Empty board → queue victory. Otherwise apply due ceiling movement and run danger-line checks.
7. Recompute nervous neighbours, routes and ammo, but do not depart runners until the next Aiming phase.
8. Present effects, then Aiming or Ending. Return framework completion only after Ending hold.

Graph blast radius is computed over valid board coordinates on a finite board, through empty cells; snapshot all affected angry centres before removal. Implement as queue+visited with stable id ordering. Flood-fill ceiling support after the full union removal. All presentation actors have finite lifetimes and caps; their truncation must not change logical occupancy.

## 6. Tick order and determinism

`Game::handle` only captures intent, pointer ownership, held keys and a one-shot fire request. It must not move, remove, score, sample global randomness or advance timers. Important audit finding: the Game trait comment says handle is called per displayed frame, while actual App::advance batches input at the next simulation advance. Code to the actual behaviour: handle once can precede multiple updates. Retain held state until replaced; consume fire exactly once in update.

`update(FIXED_DT)` uses an integer tick counter. Aiming tick: apply latest aim input; refresh fear prediction; consume valid fire before autonomous escape; otherwise update escape timers; if a departure occurs enter Escaping. Other phases advance their own bounded timer/flight. Never run several transitions recursively without a finite bound. Frame 0 remains the state before simulation, matching template capture.

Use round seed + rules + level + ordered per-tick commands for reproducible headless scenarios. Separate gameplay RNG from cosmetic RNG/hash phases; a blink cannot change ammunition. Store RNG state in the round. No draw-time random sampling, system clock, global macroquad RNG or unordered traversal in logic. Guarantee same-build deterministic behaviour; cross-platform bitwise float identity is not promised. Fixtures compare contacts and rule results on Linux/macOS within documented geometric tolerance.

`draw(&self)` is read-only and may execute twice (window and video), at different resolutions. Compute visible poses from stored simulation state. Pause and recording backpressure freeze the same tick/time. No new accumulator, wall-time slow motion or independent animation clock.

## 7. Animation representation

Keep collision Cell separate from pose. `Pose` has local translation, angle, scale_x/y, eyelid openness, pupil direction, brow angles and mouth parameters. Evaluate pure normalized local coordinates, then apply body transform and View scaling. Only decorative particles or fall actors may leave cells. Entity-id-derived phases decorrelate idle movement deterministically.

The framework View currently offers rect/circle/line/text/image, but no arbitrary polygon or ellipse primitive. Add small generic View methods for triangle/polygon and ellipse (or triangulate ellipses into triangles), using the same private View pixel mapping internally. Do not reproduce pixel offsets in game code or call raw window-size functions. Add mapping/vertex tests and screenshot checks. Record these additions in the framework patch ledger.

## 8. Two necessary integration seams

### Round outcome and retry

Audited `RoundResult` has only `score`; App treats every `Some` as a success, plays Success, and enables Next. Add a minimal generic `RoundOutcome { Won, Lost }` to RoundResult with explicit initializers. Abort stays `None`. Update App/results/i18n/test games so loss gets a neutral/loss SFX and Retry at the same level; win enables Next. A failed round must still finish capture and permit Save/Discard. Do not encode defeat as score=0 or abuse abort=None, which loses the outcome.

Retry uses the same level-derived seed and frozen round options. Template results should remain game-agnostic: no awareness of Angry, runners or family types. Keep the extended API and tests in a small recorded patch. Extra statistics can stay in an in-game ending overlay in v1 rather than bloating the trait.

### Game options without a hidden global

The existing constructor is `Game::new(level)`; no generic options argument exists. Avoid inventing that hook or a global mutable configuration. Use a game-local Setup phase: `new(level)` creates a pure default state; first handle lazily loads game settings via the persistence adapter once and shows options; Start snapshots validated options and builds the board in update. A test constructor `from_options(level, options, seed)` bypasses IO/setup for headless rules. Retry loads persisted identical options and derives identical seed unless the player explicitly changes them.

Setup UI and save buttons live in the game module. Serialize through a game-owned file in `settings::data_dir()`; do not add game fields to framework Settings. Loading/saving can happen at setup input boundaries, never in draw or every simulation tick. Small bounded JSON only, error message without panic. This uses framework recording as-is: recording starts with the round and may include setup. Before v1, playtest whether this is acceptable; if not, propose a separate reviewed generic pre-round hook rather than clandestinely replacing the recorder.

## 9. Dependencies and framework updates

Use existing serde/serde_json; no mandatory new crates. Keep the vendored miniquad patch and lockfile. Names go through config.rs and the game-name script; verify current script before using it. Preserve GPL-3.0-or-later, LICENSES/MIT-RustOut.txt and notices.

Do not blindly run update-framework.sh on the game: it overwrites game.rs, app.rs, view.rs, screens.rs, AGENTS.md and other changed integration files. Maintain `docs/FRAMEWORK_PATCHES.md` in the eventual game repo listing exact modifications, purpose, tests and upstream baseline. Update on a clean branch, manually merge/reapply patches and check all changes. This is a documented limitation, not a request to fix the base template as part of this project.
